# Design

## Context

- `ReportService.create_by_reporter_id` checks self-report and target existence, then `repository.create(...)`.
- `Report.__table_args__` has the `not_self` check and the `(status, created_at)` index; `reporter_id` and `target_id`
  are indexed through `index=True`. There is no partial unique index.
- `BanRepository.get_active` filters `lifted_at IS NULL` and a non-expired `expires_at`; `has_unlifted` ignores the
  expiry. `BanService.create` uses `has_unlifted`, the account code uses `get_active`.
- `BanService.create` already locks the user row (`align-accounts`).

## Goals / Non-Goals

**Goals:**

- The one-open-report rule holds under concurrency without an extra lock.
- "Active ban" has one definition.

**Non-Goals:**

- Hiding banned users from matches and blocking reactions to them (`add-matches`).
- `PATCH` schemas forbidding unknown fields: `BaseUpdateSchema` does not inherit `extra="forbid"` today; that is a
  `core` fix of its own, reported separately.

## Decisions

### Repeated report through `INSERT … ON CONFLICT DO NOTHING`

`ReportRepository.create_if_no_open(data)` inserts with
`on_conflict_do_nothing(index_elements=[reporter_id, target_id], index_where=status == 'open')`, which targets the new
partial unique index, and returns the row or `None`. On `None` the service reads the open report with
`get_open(reporter_id, target_id)` and returns it with `is_created = False`; the router answers 201 or 200 like
`POST /users`. Two simultaneous reports: the second insert waits for the first transaction and then does nothing, so
exactly one row exists and both requests succeed.

*Alternative:* check-then-insert under `SELECT … FOR UPDATE` of the reporter — rejected: the partial index is
required by `models.md` anyway, and `ON CONFLICT` uses it directly.

The index is declared as `Index(None, reporter_id, target_id, unique=True, postgresql_where=status == 'open')` and is
named `ix_reports_reporter_id_target_id` by the convention. It is not added to the `IntegrityError` mapping: the
service never lets it surface.

### Review statuses as a `Literal`

`ReportUpdateSchema.status` becomes `Literal[ReportStatus.RESOLVED, ReportStatus.DISMISSED]`, so `open` fails schema
validation (400 `VALIDATION_ERROR`, type `literal_error`) and cannot collide with the partial index on reopen.

### Bans without an end date

`expires_at` is removed from the model, `BanReadSchema`, `BanCreateSchema` (with its future-date validator) and
`BanUpdateSchema`. `get_active` filters `lifted_at IS NULL` only; `has_unlifted` is removed and `BanService.create`
calls `get_active(...) is not None`. The migration is autogenerated (drop column + create index).

## Risks / Trade-offs

- [Bans that had expired become active again once the column is gone] → documented in the proposal; a person lifts
  them before applying the migration. The test database starts empty.
- [Existing duplicate open reports block the index creation] → same: closed by a person first.
